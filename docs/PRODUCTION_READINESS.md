# StayEasy — production-readiness gates

## Authentication foundation currently implemented (not launch-ready)

- The backend exposes `/auth/register`, `/auth/verify-email`, `/auth/resend-verification`, `/auth/login`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/me` and `/auth/logout`.
- Passwords are stored as scrypt hashes. Verification/reset codes are short-lived (15 minutes), hashed with a server-secret HMAC, limited to five attempts, and never returned in API responses or written to application logs. Sign-in locks after five failed passwords for 15 minutes.
- Real account access tokens carry an auth version checked against the database on each request. Password resets and logout invalidate existing account tokens. Tokens are still short-lived bearer credentials, not refresh tokens.
- Registration always creates a `customer` role. Requesting the Owner workspace records intent only; it cannot confer owner permissions. An admin-only owner-request queue, decision endpoint, audit event and Android review screen are implemented in the Owner access workflow; production launch still requires staging acceptance, a verified operational admin account, operator MFA and external rate limiting. The Tenant/Owner choice screen only switches local preview UI; signed-in customers are routed back to their account until Owner access is approved, while signed-out users can only enter clearly labelled preview mode.
- Configure email through environment variables: `SMTP_HOST`, `SMTP_FROM_EMAIL`, `SMTP_PORT` (587 with STARTTLS, or 465 with TLS), and optional `SMTP_USERNAME` / `SMTP_PASSWORD`. Registration and recovery fail clearly when SMTP is unavailable; no email provider has been configured by this code change.
- Alembic bootstrap is added. Run `python -m alembic -c backend/alembic.ini upgrade head`. The first revision uses the current SQLAlchemy metadata to create missing tables; before public production, freeze/review it as an explicit schema baseline and compare it against any existing database. Do not treat this bootstrap as a completed migration audit.
- Interactive Android screens are wired for account creation, email verification, sign-in, password recovery, account status, Owner access requests and sign-out. An administrator screen lists Owner requests and submits server-validated approve/reject decisions; approvals promote the role server-side, record an audit event and invalidate existing applicant tokens. Account access tokens are encrypted with AES-GCM using an Android Keystore key and are bound to a single API origin; app startup restores the token and validates it against `/auth/me`. Refresh-token rotation, device/session management, external rate limiting, MFA, account deletion, production SMTP configuration, signed release and independent security review remain release gates.

## Must be completed before public launch

- Finish production Android/API integration using the server-backed finance ledger as the current vertical slice. Add refresh-token rotation, device/session management, explicit server-confirmed state and consistent loading/error/offline reconciliation across every workflow. Do not assume local demo records have synced.
- The account API includes verified registration, email verification, sign-in, password recovery, server-side session invalidation and an admin-reviewed Owner access workflow. Tenant move-out requests and owner review are now server-backed with notice-period enforcement, review notes, notifications and audit events. Before launch, verify both journeys end-to-end against staging, configure production email delivery and operator MFA, add external rate limits/edge protections, and complete end-to-end sync for every remaining workflow. Owner workspace intent must never confer permissions.
- Apply Alembic migrations; do not rely on ORM `create_all()` after real customer data exists. Back up the database and rehearse restore/PITR.
- Add secure object storage with signed uploads/downloads, image type/size validation, malware screening, compression, moderation and access controls for documents.
- Configure Maps SDK, Places API and routing only with restricted keys, billing controls, data minimization and attribution. Never display uncomputed distances as facts.
- Integrate a payment provider and verify webhooks server-side. Idempotency, settlement, refunds, chargebacks and provider reconciliation must have automated tests. Manual ledger rows must remain visibly distinct from provider-confirmed payments.
- Add notification delivery workers, push tokens, email/SMS provider templates, retries, idempotency and delivery status.
- Add scheduled billing/expiry/availability reminders and idempotent jobs; test time zones, pro-rata policies, notice periods and edge dates.
- Complete privacy requests, data export, account deletion, retention schedule, consent records and independent legal/privacy review before production. An expiry-aware encrypted invitation-document purge command is implemented at `python -m backend.scripts.purge_expired_invitation_documents` (supports `--dry-run`). It needs `DOCUMENT_STORAGE_ROOT` configured to the exact private API storage directory and a daily scheduled invocation; alert on non-zero exit/failure counts. This command does not replace a complete account-deletion/export workflow or legal approval.
- Add abuse reporting, fraud escalation, verified-review moderation, appeal workflow, evidence retention, admin action logs and staff offboarding.
- Add rate limits, input/output limits, request IDs, safe error responses, audit monitoring, dependency scanning, vulnerability review, incident response and HTTPS reverse proxy.
- Test tenant isolation and cross-property staff scopes; test reservation races against PostgreSQL with parallel requests.
- Complete Android UI tests, API tests, migration tests, accessibility test, small/large device test, low-connectivity test, crash analytics and staged release checks.

## Scope explicitly not claimed as complete

The current package is an implementation foundation, not a public launch-ready marketplace. A development-session-backed finance sync and manual ledger flow exist, but production identity/session management and end-to-end sync for every workflow are not complete. Google Maps/Places, real payment processing/webhooks, push notification delivery, document/object storage, database migrations, production deployment, full multilingual resources, iOS and subscription billing are not active integrations.
